# github-ci v1.1.0 Design

## Status and release policy

This document defines the replacement adoption contract for `github-ci`.
Release `v1.1.0` is intentionally a clean, pre-adoption compatibility reset.
It is not backward compatible with the configuration and reusable-workflow
interfaces published in `v1.0.0`.

This one-time exception is safe operationally because no repository adopted
`v1.0.0`, but it is not a backward-compatible Semantic Versioning minor
release. The release notes and adoption documentation must say so directly.
The `v1.0.0` tag and GitHub Release remain immutable historical records and
must not be deleted, moved, or recreated. Compatibility guarantees for future
`1.x` releases begin at `v1.1.0`.

No `v1.1.0` tag or GitHub Release may be created until the exact candidate
commit passes the release-acceptance process in this document. Tagging and
publishing remain separately authorized actions.

## Verified problems

The following defects exist in `v1.0.0`:

- `build-tags` is parsed and validated but is not applied to any Go command.
- The deep workflow always starts PostgreSQL and Redis and always executes the
  hardcoded `integration` build tag, regardless of configured services.
- `go-strict` and `go-library` select the same applicability catalog and the
  same workflow behavior.
- Build, test, vet, staticcheck, golangci-lint, govulncheck, compatibility,
  CodeQL, portability, fuzz, and benchmark commands hardcode broad defaults
  instead of consuming a single validated execution contract.
- The deep portability job operates only at the checkout root and therefore
  does not prove multi-module compatibility.
- The adoption guide identifies a failed `repository-only` run as a successful
  Go consumer canary. Every Go job in that run was skipped and the final gate
  failed.
- The exact `v1.0.0` release commit passed the standard and release-evidence
  workflows but did not run the deep workflow and did not pass a Go consumer
  canary.

The existing strict parsers, fail-closed evidence gate, action SHA pins,
container digests, least-privilege permissions, hardened Linux runners,
immutable release evidence, SBOM generation, and provenance attestations are
preserved.

## Goals

`v1.1.0` must:

1. make every documented consumer field effective;
2. provide one typed source of truth for every Go command line;
3. support multi-module repositories and module-specific execution settings;
4. apply package scope, module mode, build tags, timeout, parallelism, race
   limits, and coverage scope consistently;
5. give `go-strict`, `go-library`, and `repository-only` distinct contracts;
6. leave repository-specific services, authentication, and generation under
   consumer ownership;
7. document scanner ownership without weakening or deduplicating blocking
   findings;
8. keep expensive assurance scheduled or explicitly dispatched;
9. reject a release candidate unless standard, deep, and external consumer
   evidence all bind to the exact candidate commit; and
10. prove untrusted-fork behavior without granting repository secrets.

## Non-goals

The central workflows do not:

- execute arbitrary consumer-provided shell commands;
- receive private dependency credentials;
- guess how a repository generates source code;
- own a consumer's database schema, migrations, fixtures, or service topology;
- replace repository-specific protocol, wire, integration, or system tests;
- hide one scanner's finding because another scanner reported a similar issue;
- make mutation testing, full-history scanning, benchmarks, or multi-platform
  testing part of every pull request; or
- create, move, delete, or publish Git tags and GitHub Releases.

## Consumer configuration schema 2

`v1.1.0` accepts only `schema-version: 2`. A schema-1 configuration fails
preflight with a migration error that names `v1.1.0` and the adoption guide.
There is no silent translation layer.

The complete configuration shape is:

```yaml
schema-version: 2
profile: go-library
go:
  defaults:
    packages: [./...]
    module-mode: readonly
    build-tags: []
    test-timeout: 10m
    package-parallelism: 4
    race-parallelism: 1
    coverage-packages: [./...]
  modules:
    - path: .
    - path: tools
      packages: [./...]
      build-tags: [tooling, sqlite]
      test-timeout: 15m
      package-parallelism: 2
      race-parallelism: 1
      coverage-packages: [./...]
generated-paths:
  - internal/generated
exceptions: .github/github-ci-exceptions.yaml
```

### Discovery and inheritance

For Go profiles, `go` is optional. When `go.modules` is omitted, preflight
discovers every tracked `go.mod` and applies `go.defaults` to each module. When
`go.modules` is present, its paths must exactly equal the tracked module set.
The root module is `.`. Nested modules are executed independently and excluded
from their parents' recursive package traversal by the Go toolchain.

Each module inherits every omitted field from `go.defaults`. Module values
replace, rather than append to, inherited lists. Built-in defaults are applied
when both levels omit a field:

| Field | Built-in default | Meaning |
| --- | --- | --- |
| `packages` | `[./...]` | Package patterns supplied to applicable tools |
| `module-mode` | `readonly` | Go module download/write policy |
| `build-tags` | `[]` | Additional satisfied Go build constraints |
| `test-timeout` | `10m` | Per-package test-binary timeout |
| `package-parallelism` | `4` | Concurrent Go build programs or test packages |
| `race-parallelism` | `1` | Race package and in-binary test concurrency |
| `coverage-packages` | `[./...]` | Packages instrumented for coverage |

An explicitly empty `coverage-packages` list selects Go's package-local
coverage behavior and omits `-coverpkg`. Other empty lists are accepted only
where the table defines an empty default.

### Validation

Configuration decoding remains strict: unknown fields, duplicate keys,
multiple YAML documents, aliases that create ambiguous structures, and trailing
data are rejected.

Module paths and generated paths remain repository-relative, slash-separated,
and traversal-free. Package patterns must be nonempty, must not begin with a
dash, and must not contain controls, whitespace, backslashes, shell syntax,
version-query suffixes, absolute filesystem paths, or traversal segments. Go's
`...` wildcard is permitted only as a complete path element or suffix accepted
by the Go tool.

`module-mode` is exactly one of `readonly`, `vendor`, or `mod`. Build tags use
the existing alphanumeric, underscore, dot pattern and must be unique.
`test-timeout` must be a positive Go duration no greater than 45 minutes.
Package parallelism is between 1 and 64. Race parallelism is between 1 and 16.
All lists reject duplicates and enforce conservative size limits.

`repository-only` must not contain a `go` block and remains invalid when the
tracked repository contains a `go.mod`. Go profiles require at least one
tracked module.

The `services` and `generated` schema-1 fields are removed. Schema 2 uses
`generated-paths` solely to classify committed generated files; it never
claims to know the generator command.

## Assurance profiles

Every applicable finding remains blocking.

- `repository-only` runs repository, workflow, secret, source, infrastructure,
  supply-chain, and dependency-change checks that do not require a Go module.
- `go-strict` adds the complete Go correctness, race, analysis, vulnerability,
  compatibility, and coverage policy.
- `go-library` contains the complete `go-strict` policy and additionally
  requires public API compatibility through `apidiff`.

The applicability catalog and locked tool profiles must encode this difference.
No workflow branch may infer profile behavior from an unvalidated caller input.
Preflight reads the consumer configuration and exposes only validated profile
and capability outputs to downstream job conditions.

## Typed Go execution plan

A new focused Go package resolves configuration into immutable per-module
execution plans. The public CLI emits canonical JSON containing the module
directory, environment entries, and ordered argument arrays. Shell scripts
load JSON values into Bash arrays and execute them with quoted array expansion.
They must never use `eval`, concatenate user values into commands, or rely on
word splitting.

Each serialized module contains an `invocations` object keyed by the supported
tool name. Every value contains an `environment` string array and an ordered
`arguments` array whose first element is the executable. The planner owns flag
translation:

| Command | Applied controls |
| --- | --- |
| `go build` | module mode, package parallelism, build tags, package scope |
| `go test` | module mode, package parallelism, build tags, timeout, coverage scope, package scope, uncached execution |
| `go test -race` | module mode, race parallelism through `-p` and `-parallel`, build tags, timeout, package scope, uncached execution |
| `go vet` | module mode, package parallelism, build tags, package scope |
| gopls | module mode and build tags through the Go environment; tracked files remain the diagnostic scope |
| staticcheck | build tags and package scope; module mode through the Go environment |
| golangci-lint | module download mode, build tags, concurrency, timeout-safe job execution, package scope |
| govulncheck | module mode, build tags, package scope, and bounded Go runtime concurrency |
| CodeQL manual build | the same build plan used by `go build` |
| compatibility and portability | the same build and test plans for every resolved module |
| fuzz and benchmark discovery | module mode, build tags, and configured package scope |

Tools that do not expose package concurrency receive a bounded `GOMAXPROCS`
instead of an invented unsupported flag. Direct tool flags and environment
behavior must be verified against the pinned tool versions before generation.

The standard and deep workflows consume the same serialized execution plan.
No workflow may reconstruct defaults independently.

## Standard workflow

Preflight checks out the consumer and workflow helper at immutable identities,
validates schema 2, discovers modules, resolves command plans, calculates the
existing applicability and policy digests, and uploads a single plan artifact.
It exports validated profile and Go-applicability outputs.

Formatting, correctness, tests, analysis, compatibility, CodeQL, security,
supply-chain, and repository jobs continue to produce native reports and
normalized evidence. The aggregate gate retains its existing fail-closed
handling for missing, malformed, stale, duplicate, skipped, cancelled, or
unexpected evidence.

Workflow-call inputs that duplicate versioned policy or consumer configuration
are removed. The standard reusable workflow accepts only `config-path`; Go
toolchain versions come from the reviewed central policy lock. This is part of
the intentional v1.1.0 interface reset.

## Deep workflow

Deep assurance remains scheduled and manually dispatchable. It gains its own
schema-2 preflight and uses the same module plans as standard assurance.

The portability matrix runs every configured module on Linux, macOS, and
Windows with the current and previous supported Go versions. Fuzz target
discovery and benchmarks honor module package scope and build tags. Mutation
testing remains complete and fail-closed for every configured module.
Full-history secret scanning and dependency freshness remain scheduled.

The central PostgreSQL and Redis service job is removed. The deep gate requires
every remaining deep job to complete successfully and treats skips,
cancellations, and timeouts as failures.

## Consumer-owned preparation and integration

Reusable workflow jobs are isolated. A caller's preparation job cannot inject
credentials, a modified workspace, or running containers into a called
workflow's jobs. Documentation therefore provides separate, independently
required consumer jobs:

- a generated-source job runs the repository's generator and fails on a dirty
  tracked diff;
- PostgreSQL and Redis examples use digest-pinned services and run the
  repository's own integration command and tags;
- private dependency jobs run only on trusted events, configure authentication
  locally, and never expose credentials to fork pull requests; and
- protocol and system tests remain repository-owned and use their required
  operating system or container topology.

The governance manifest changes from one `required-check` string to a strict,
nonempty `required-checks` array. Each configured name must have been observed
in a real canary run. Governance never guesses local preparation check names.

## Scanner ownership matrix

The policy documentation adds an ownership matrix with one primary purpose per
scanner and a reason for every overlap:

- CodeQL owns compiled semantic dataflow; Semgrep owns portable pattern rules;
  golangci-lint's gosec owns Go-specific source idioms.
- govulncheck owns reachable Go vulnerability analysis; OSV-Scanner owns
  manifest and lockfile package matching; Trivy owns broad filesystem and
  operating-system inventory; Grype cross-checks the generated SBOM.
- GitHub secret scanning owns platform alert lifecycle; Gitleaks owns blocking
  pull-request content and scheduled full-history scans; Trivy contributes
  independent filesystem secret patterns.
- Dependency Review owns pull-request dependency deltas; SBOM scanners own the
  complete resolved inventory.

"Primary" identifies triage and policy ownership. It does not suppress another
scanner's result. Every applicable scanner still emits evidence and blocks on
findings or execution errors.

## Release acceptance

A repository-level `release-candidate` workflow verifies one exact candidate
commit. It must not create a tag or release. Its final gate requires:

1. the local standard reusable workflow at the candidate commit;
2. the local deep reusable workflow at the same commit;
3. a successful standard run in a separate public Go canary repository whose
   caller pins the exact candidate commit;
4. a successful deep run in that canary at the same workflow commit;
5. a successful pull-request run whose head repository differs from the base
   repository, proving the untrusted-fork path; and
6. validated canary configuration containing multiple tracked modules, at
   least two build tags, generated-source classification, explicit package
   scope, module mode, timeout, parallelism, race limits, and coverage scope.

The release-acceptance verifier uses the public GitHub API and fail-closed JSON
decoding. It verifies repository visibility, run event, run conclusion, run
head SHA, pull-request head/base repository identity, caller contents, exact
40-character workflow pin, and canary configuration at the run's immutable
commit. HTTP errors, missing fields, pagination gaps, cancelled runs, mutable
refs, mismatched SHAs, and malformed YAML fail verification.

The candidate workflow uploads a canonical acceptance record containing all
verified repository, run, commit, and workflow identities. The tag-triggered
release-evidence workflow searches for a successful release-candidate run at
the exact tagged commit, downloads and revalidates that record, and includes it
in the checksummed, attested release evidence. A successful run for another
commit is never reusable.

The dedicated canary is public and contains no production code or credentials.
Its generated fixtures exercise the supported contract without depending on a
consumer's unrelated history. Live fork proof requires a second GitHub user or
organization namespace; a same-repository branch is not equivalent.

## Migration and adoption

The adoption guide replaces schema-1 examples with schema 2 and includes a
field-by-field migration table. It states that `v1.0.0` was not successfully
canary-validated and is not an adoption target. It does not claim that the
historical tag was moved or withdrawn.

Callers pin the exact `v1.1.0` commit SHA. The semantic tag is review context,
not an executable trust anchor. Existing action full-SHA pins, container
digests, default `contents: read`, isolated CodeQL `security-events: write`, and
release-only OIDC/attestation permissions remain unchanged or narrower.

## Test strategy

Implementation follows red-green-refactor for every behavior.

- Configuration unit tests cover defaults, overrides, explicit empty coverage,
  every boundary, duplicate collections, invalid patterns, invalid durations,
  zero and excessive parallelism, schema-1 rejection, and profile constraints.
- Configuration fuzz tests seed schema-1, schema-2, malformed YAML, aliases,
  duplicate keys, controls, traversal, and command-shaped input.
- Execution-plan unit tests assert exact argument order and environment for
  every command, with and without tags, for each module mode and package scope.
- A shell integration harness uses fake executables that record NUL-safe argv
  and environment values, proving the production scripts execute exactly the
  planned arguments without evaluation or splitting.
- Multi-module fixtures cover root and nested modules, distinct module
  overrides, multiple tags, generated source, vendor mode, explicit package
  subsets, package-local coverage, and module-wide coverage.
- Workflow golden tests assert preflight outputs, job conditions, plan reuse,
  removal of central services, exact permissions, pinned actions, timeouts,
  scheduled deep triggers, and fail-closed gates.
- Governance tests cover multiple required checks, duplicates, empty lists,
  observed-name enforcement, idempotent planning, and exact REST mutations.
- Release-acceptance tests use controlled HTTP servers for successful runs,
  fork identity, pagination, malformed responses, stale SHAs, mutable caller
  refs, failed and cancelled jobs, private repositories, and missing evidence.
- Each regression assertion is mutation-tested by reverting or corrupting the
  corresponding production behavior and observing the intended test failure.
- The full Go validation sequence is build, uncached tests, vet, staticcheck,
  golangci-lint, goimports, gopls, race tests, generated-artifact verification,
  and repository workflow/security validation.
- Final acceptance uses actual GitHub standard, deep, external canary, and fork
  runs at the exact release candidate commit.

## Acceptance criteria

`v1.1.0` is ready for tagging only when:

1. schema 2 has no documented field without execution behavior;
2. all Go command families consume the typed module plan;
3. `go-library` has an enforced library-specific policy difference;
4. no central workflow starts PostgreSQL or Redis or accepts private
   credentials or arbitrary generation commands;
5. the scanner ownership matrix covers every intentional overlap;
6. standard and deep workflows pass at the exact candidate commit;
7. a separate public Go canary passes standard and deep workflows while
   exercising every schema-2 control;
8. an untrusted-fork pull request passes without secrets;
9. release evidence binds the successful acceptance record, SBOMs, checksums,
   source archive, callers, and provenance to the same commit;
10. all automated tests and linters pass, including race and deliberate
    mutation checks; and
11. no tag or GitHub Release has been created, moved, deleted, or published
    without explicit authorization.
